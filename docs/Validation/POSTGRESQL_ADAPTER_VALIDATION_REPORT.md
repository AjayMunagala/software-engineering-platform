# PostgreSQL Persistence Adapter Validation Report

## Status

- Phase: 3.4.3 — PostgreSQL Persistence Adapter
- Evidence date: 2026-07-25
- Result: accepted
- Governance: engineering acceptance recorded on 2026-07-26
- Phase 3.4.4: authorized

## Scope

The candidate adapter implements the accepted storage-neutral persistence port
against the frozen PostgreSQL 18 schema. It owns parameterized SQL, lifecycle
transactions, fixed ordered 4 MiB chunks, exact-byte verification, atomic scan
publication, scope-filtered reads, projections, diagnostics, statistics,
retention, garbage collection, and safe error translation.

It does not run migrations at application startup, construct a connection
pool, read environment variables, load credentials, expose APIs, import an
intelligence engine, or serialize an intelligence artifact.

## Compatibility Correction Before SQL Implementation

Adapter mapping found four candidate fields that were not losslessly
representable by the already frozen physical schema. Because the neutral port
is still `0.1.0`, the candidate was corrected before adapter SQL was written:

- repository canonical text became a proof-bearing `SourceIdentity`;
- scan producer became `AnalysisProfileDigest` plus optional source revision;
- publication became scan-keyed and gained the required manifest scheme;
- arbitrary artifact attributes were removed; bounded projections remain the
  query-oriented extension point.

Artifact stable-ID evidence is one optional scheme identity, matching the
frozen envelope column. These changes preserve the accepted lifecycle,
integrity, scope, and storage-neutrality decisions and prevent silent data
loss in the adapter.

## Dependency and Security Audit

- pgx imports exist only inside `backend/internal/storage/postgres`.
- `backend/persistence`, RIE, and LIE contain no SQL or driver dependency.
- The adapter accepts a supplied database capability and never constructs a
  production pool.
- No password, authenticated URL, `.env`, private key, or connection setting is
  committed.
- SQL uses parameters; driver errors and constraint details stay private.
- Cross-scope target operations return `not_found` without exposing existence.

## Known Boundaries

- PostgreSQL physical IDs are UUID-form neutral strings; request IDs remain
  neutral and are deterministically mapped to audit correlation UUIDs.
- Runtime pool sizing, TLS, health checks, and environment configuration remain
  Phase 3.5 work.
- Phase 3.4.4 still owns the final API/naming review, performance comparison,
  documentation audit, and `1.0.0` freeze.

## Conclusion

Phase 3.4.3 implementation and validation satisfy the documented exit gate.
Engineering accepted the milestone and ADR 0014 on 2026-07-26 and authorized
Phase 3.4.4 only. The persistence contract remains a `0.1.0` candidate until
the Phase 3.4.4 API, performance, security, dependency, conformance, and
documentation reviews complete. Credentials, APIs, UI, and runtime
orchestration remain unauthorized.
